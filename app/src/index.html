How a revoke is proven.

  1. One finalized read of the token account, its owner, its delegate, the clock and the token program. The program bytes must match a verified build.

  2. The revoke is simulated in the same finalized bank. The result must equal the expected account change exactly, or nothing is offered for signing.

  3. Your wallet signs the reviewed bytes only. The message and signature are checked again before anything is sent.

  4. The finalized transaction is fetched, the account is observed again, and the permission must be absent before the page says revoked.

Authority, not balances.

Token delegates and subscriptions are read by separate adapters and compiled into one record: who, capability, resource, limit, remaining, lifecycle. The console renders that record, not a screen per protocol.

A subscription's on-chain delegate is a program address. Velon derives the merchant and pullers who can move funds through it and keeps the program address as lineage.

When several keys draw on the same allowance, Velon reports one permission with all of them as principals, so the limit is never doubled.

Each record names the finalized slot, the account bytes it came from, the program build hash and the adapter version. Open any permission in the console to see them.

An unverified program version or a missing account yields unsupported or incomplete, and no permission is shown. An empty result never claims a wallet is clean.

After signing, Velon waits for finality, reads the account again and only then reports success. The receipt replays later without contacting the chain.
